# 커밋 메시지와 PR 설명 작성

## 절대 규칙
- **변경을 읽고 쓴다.** `git diff --cached`(스테이징된 것)를 먼저 보고, 없으면 `git status`와 `git diff`로 무엇을 커밋할지 사람에게 확인한다. 추측으로 쓰지 않는다.
- **메시지와 대상 파일을 먼저 보여 준다.** 사람이 "커밋해"라고 했으면 보여 준 뒤 커밋하고, "써줘"만 했으면 메시지만 준다. 푸시·PR 생성은 사람이 요청할 때만 한다.
- **내가 만든 변경만 담는다.** 원래 있던 다른 미커밋 수정이나 비밀값 파일(.env 등)은 넣지 않고, 섞여 있으면 알린다.
- 메시지에는 **무엇이 바뀌었는지와 왜**만 쓴다. 개인 사정, 작업 목적의 사적인 맥락, 도구 이름 홍보는 쓰지 않는다.

## 1. 관례 파악
- 프로젝트 `AGENTS.md`(또는 `CLAUDE.md`)의 커밋 규칙이 있으면 그대로 따른다.
- 없으면 `git log -15 --format='%s%n%b'`로 최근 커밋의 언어, 접두어, 본문 형식을 보고 같은 형식으로 쓴다.
- 둘 다 없으면 기본 형식: 한글 Conventional Commits, 본문은 불릿 (`references/conventions.md`).

## 2. 타입 고르기
| 타입 | 언제 |
|---|---|
| `feat` | 사용자가 쓸 수 있는 기능이 새로 생김 |
| `fix` | 잘못 동작하던 것을 고침 |
| `perf` | 동작은 같고 성능(응답 시간, 처리량, 자원)이 좋아짐 |
| `refactor` | 동작·성능 변화 없이 구조만 바꿈 |
| `test` / `docs` / `chore` | 테스트만 / 문서만 / 빌드·설정·의존성 |
- 여러 종류가 섞였으면 가장 중요한 변경의 타입을 쓰고, 성격이 크게 다르면 커밋을 나누자고 제안한다.

## 3. 커밋 메시지
- 제목: `타입: 무엇을 했는지` (50자 안팎, 마침표 없음). 예: `perf: 협의 목록 캐시 TTL에 jitter를 더해 동시 만료 방지`
- 본문: 불릿 2~5개. 무엇을, 왜. 성능 변경이면 전후 숫자가 있을 때만 넣는다 (없는 숫자를 만들지 않는다).

## 4. PR 설명 (요청했을 때)
`references/conventions.md`의 PR 양식(배경 → 변경 → 검증 → 영향·위험 → 리뷰 포인트)을 따른다. 검증 칸에는 실제로 돌린 테스트·측정만 쓴다.
