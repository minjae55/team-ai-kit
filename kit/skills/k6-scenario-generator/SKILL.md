# k6 부하 테스트 시나리오 작성

## 절대 규칙
- **스크립트를 쓰기만 하고 `k6 run`은 실행하지 않는다.** 부하는 서버와 DB에 영향을 주므로 사람이 실행한다. 실행 명령은 결과에 적어 준다.
- **운영 주소를 기본값으로 넣지 않는다.** 주소는 `__ENV.BASE_URL`로 받고, 기본값은 프로젝트 AGENTS.md의 로컬·테스트 주소만 쓴다.
- 비밀번호·토큰을 새로 만들어 넣지 않는다. 프로젝트가 정한 테스트 계정 관례(AGENTS.md나 기존 스크립트)를 따르고, 없으면 `__ENV`로 받는다.

## 1. 프로젝트 관례 파악
- 프로젝트 `AGENTS.md`에서 앱 주소, 테스트 계정, 로그인 방법, k6 폴더 위치를 찾는다.
- 기존 k6 스크립트를 2~3개 읽고 **같은 구조**를 따른다: 파일 이름 규칙, 로그인 방식, 태그 이름, threshold 형식, 출력 방식.
- 대상 API의 컨트롤러·요청 DTO를 읽어 실제 경로, 메서드, 요청 본문, 응답 형식을 확인한다. 추측으로 필드를 만들지 않는다.

## 2. 목적 정하기 (요청에 없으면 기본값을 쓰고 결과에 밝힘)
| 목적 | executor | 예 |
|---|---|---|
| 동시 요청에서 정합성·경쟁 상태 재현 | `per-vu-iterations` (VU마다 1회) | 같은 재고에 동시 주문 |
| 목표 동시 사용자에서 응답 시간 | `constant-vus` 또는 `ramping-vus` | 동시 50명 1분 |
| 목표 처리량(RPS)에서 응답 시간 | `constant-arrival-rate` | 초당 100건 |
| 개선 전후 비교 | 위 중 하나를 **고정 조건**으로 | 같은 VU·시간·데이터 |

## 3. 작성 규칙
1. VU 수, 시간, 주소는 `__ENV`로 받는다 (`__ENV.VUS || '10'`, `__ENV.BASE_URL || '<로컬 주소>'`).
2. 측정할 핵심 요청에는 `tags: { name: '<이름>' }`을 붙이고, `thresholds`의 `http_req_duration{name:<이름>}`과 이름을 맞춘다. 요청에 목표(예: p95 500ms)가 있으면 threshold로 넣는다.
3. 모든 요청 뒤에 `check()`로 상태 코드와 핵심 응답 필드를 검증하고, 실패하면 상태 코드와 응답 일부를 `console.error`로 남긴다.
4. 로그인 비용을 측정에서 빼야 하면 `setup()`에서 토큰을 미리 받아 VU가 나눠 쓴다. 로그인까지 측정하려면 반복마다 로그인한다. 어느 쪽인지 주석으로 적는다.
5. 필요한 선행 데이터(상품, 옵션, 카트 등)는 조회 API로 실제 값을 받아 쓴다. ID를 하드코딩하지 않는다. 고정 데이터가 꼭 필요하면 `__ENV`로 받는다.
6. 같은 데이터에 몰리게 할지(경쟁 재현), 흩어지게 할지(일반 부하) 의도에 맞게 고르고 주석으로 적는다.
7. 골격과 예시는 `references/patterns.md`를 따른다.

## 4. 문법 확인
- `k6`가 있으면 `k6 inspect <파일>`로 문법을 확인한다 (부하를 주지 않음). 없으면 생략하고 결과에 "문법 확인 못 함"으로 적는다.

## 5. 완료 후 알려 줄 것
- 만든 파일 경로
- 실행 명령 예: `k6 run --env VUS=50 --summary-export=summary.json k6/<파일>.js`
- 무엇을 검증하는 시나리오인지, threshold와 그 근거, 기존 스크립트와 다른 점 (한두 줄)
- 실행 전에 사람이 확인할 것: 대상 환경 주소, 테스트 데이터 준비, 부하가 다른 사람에게 영향을 주지 않는지
