# 테스트 코드 작성

> 요약: 기존 관례대로 JUnit 테스트를 쓰고 실행해 통과를 확인한다

## 절대 규칙
- **명세(요청, 주석, 문서)를 기준으로 테스트한다.** 구현을 그대로 베낀 테스트는 아무것도 검증하지 않는다.
- **테스트가 실패하면 원인을 가른다.** 테스트가 틀렸으면 테스트를 고치고, 대상 코드가 명세와 다르면 **대상 코드를 몰래 고치거나 테스트를 코드에 맞추지 않는다.** 실패한 테스트와 어긋난 부분을 사람에게 알린다.
- 테스트는 직접 실행해 결과를 확인한다. 실행 명령은 프로젝트 `AGENTS.md`를 따르고, 없으면 `./gradlew test --tests '<클래스>'` 또는 `mvn -q test -Dtest=<클래스>`.
- 운영 DB나 외부 API를 부르는 테스트를 만들지 않는다 (목·테스트용 DB를 쓴다).

## 1. 관례 파악
- 기존 테스트 파일 2~3개를 읽고 같은 방식을 쓴다: 위치(`src/test/java/같은 패키지`), 이름 규칙, 단언 라이브러리(AssertJ·JUnit), 목 사용(Mockito), 표시 이름(@DisplayName).
- 빌드 파일에서 실제로 쓸 수 있는 테스트 라이브러리를 확인한다. 없는 라이브러리를 추가하지 않는다 (필요하면 사람에게 제안).

## 2. 케이스 목록 먼저
메서드마다 표로 정리한 뒤 쓴다.
- 정상: 대표 입력 1~2개
- **경계값**: 명세의 "이상/초과/이하/미만", 0, 최대값, 빈 값
- 예외: 잘못된 입력, 없는 대상, 권한 없음, 이미 처리된 상태
- 계층별: 도메인은 순수 단위 테스트, 서비스는 Mockito(@Mock/@InjectMocks), 컨트롤러는 @WebMvcTest+MockMvc, 리포지토리는 @DataJpaTest

## 3. 작성 규칙
- 이름: 프로젝트 관례, 없으면 `메서드_상황_기대결과` (예: `discount_최소주문금액과_같으면_할인적용`)
- Given-When-Then으로 나누고, 테스트 하나에 검증 하나
- 고정 시각이 필요하면 `Clock`을 주입받는 구조인지 보고, 아니면 사람에게 제안한다

## 4. 실행과 보고
- 실행 결과(통과 N개, 실패 M개)를 그대로 알린다.
- 덮은 케이스 목록(정상·경계·예외)과, 명세와 다르게 동작해서 실패한 부분이 있으면 그 내용과 근거(명세 문장, 실패 메시지)를 알린다.
