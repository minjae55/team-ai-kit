# 코드 리뷰

> 요약: 변경 코드에서 버그·보안·트랜잭션·성능 문제를 근거와 함께 찾는다

## 절대 규칙
- **확인한 문제만 쓴다.** 문제마다 파일:줄, 어떤 입력·상황에서 무엇이 잘못되는지(실패 시나리오), 고치는 방법을 붙인다. 시나리오를 못 대면 "확인 필요"로 낮춘다.
- **코드를 고치지 않는다.** 사람이 고쳐 달라고 할 때만 고친다.
- 취향(이름, 포맷)은 사람이 원할 때만 짧게 덧붙인다. 중요한 문제를 묻히게 하지 않는다.
- 문제가 없으면 "중요한 문제를 찾지 못함"이라고 쓰고, 무엇을 확인했는지 적는다. 억지로 지적을 만들지 않는다.

## 1. 범위 정하기
- 사람이 정하지 않았으면: 스테이징된 변경(`git diff --cached`) → 없으면 작업 중 변경(`git diff`) → 없으면 기본 브랜치와의 차이(`git diff main...HEAD`)
- 바뀐 줄만 보지 말고, 바뀐 메서드를 부르는 쪽과 불리는 쪽을 열어 맥락을 확인한다.
- 프로젝트 `AGENTS.md`의 규칙(트랜잭션 정책, 금지 패턴 등)이 있으면 함께 본다.

## 2. 보는 순서 (중요한 순)
`references/checklist.md`를 따른다. 요약:
1. **정확성**: 조건 반대, 경계값, null, 예외를 삼킴, 잘못된 상태 전이
2. **보안**: SQL·명령 주입(문자열로 쿼리 조립), 권한 확인 누락(남의 데이터 접근), 비밀값·개인정보 로그 출력
3. **트랜잭션·동시성**: `@Transactional`이 실제로 안 걸리는 경우(같은 클래스 안 호출, private 메서드), 재고·포인트 같은 공유 자원 경쟁, 외부 호출을 트랜잭션 안에서
4. **성능**: 반복문 안 쿼리(N+1), 페이지 없는 전체 조회, 인덱스를 못 타는 조건
5. **테스트**: 바뀐 동작을 검증하는 테스트가 있는지

## 3. 결과 출력 (이 형식 그대로)
```markdown
## 요약
(머지 전에 꼭 고칠 것 N개 / 고치면 좋은 것 M개, 한 줄 결론)

## 꼭 고칠 것
### 1. <문제> — `파일:줄`
- 실패 시나리오: <입력·상황 → 잘못된 결과>
- 수정 제안: <방법, 필요하면 짧은 코드>

## 고치면 좋은 것
- ...

## 확인한 것
- (본 범위와 확인한 항목, 확인 못 한 것)
```
