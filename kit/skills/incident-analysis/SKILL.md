# 장애·지표 이상 원인 분석

## 절대 규칙
- **읽기만 한다.** 재시작, 배포, 설정 변경, DB 쓰기·DDL, 캐시 삭제, 부하 테스트 실행을 하지 않는다. 필요하면 "사람 승인 필요"로 제안만 한다.
- **근거 없는 원인은 쓰지 않는다.** 원인 후보마다 실제로 조회한 수치(지표 이름, 시각, 값)를 붙인다. 근거가 부족하면 "추가 확인 필요"로 분류한다.
- 비밀값 파일(.env, 접속 정보 파일)은 열지 않는다. 스크립트에 경로만 넘긴다.

## 1. 입력 정리
다음 세 가지를 확인한다. 빠졌으면 사람에게 묻되, 대략적인 값으로 시작해도 된다.
- **시간 범위**: 언제부터 언제까지 (예: "14:00~14:20", "최근 30분")
- **대상**: 서비스, API, 기능 (예: `POST /api/buyer/orders`)
- **증상**: 느림, 에러, 타임아웃, 알림 내용 등
- (부하 테스트였다면) 어떤 스크립트를 몇 명(VU)으로 돌렸는지. 모르면 묻지 말고 "확인 못 함"으로 둔다

## 2. 프로젝트 맥락 읽기
현재 프로젝트의 `AGENTS.md`(또는 `CLAUDE.md`)에서 다음을 찾는다. 이 스킬은 프로젝트별 값을 갖고 있지 않다.
- 지표 시스템 주소와 주요 PromQL
- DB 접근 방법 (컨테이너 이름, 접속 정보 파일 경로)
- 로그 위치, 알려진 과거 원인

## 3. 근거 수집 (이 순서대로)
스크립트는 이 SKILL.md가 있는 폴더의 `scripts/` 안에 있다. 증상별로 무엇을 볼지는 `references/checklist.md`를 따른다.
- 스크립트는 **전체 경로로 직접** 호출한다 (`python3 /…/scripts/prom_query.py …`, `bash /…/scripts/db_query.sh …`). `S="bash /…"; $S …`처럼 명령을 변수에 담으면 zsh에서 실패한다 (zsh는 변수를 공백으로 나누지 않음).

**3-1. 지표** — `scripts/prom_query.py`
- 이상 구간과, 바로 앞의 같은 길이 정상 구간을 **둘 다** 조회해서 비교한다.
- 순서: 응답 시간(p95) → 처리량·에러 → 커넥션 풀 → DB 지표.
```bash
python3 scripts/prom_query.py --start 2026-11-25T14:00 --end 2026-11-25T14:20 \
  'histogram_quantile(0.95, sum by (le) (rate(http_server_requests_seconds_bucket{uri="/api/buyer/orders"}[30s])))'
```

- 결과가 비면 "지표가 없다"고 결론 내리기 전에 라벨 없이 존재 여부부터 확인한다 (예: `count by (uri) (http_server_requests_seconds_bucket)`).

**3-2. DB** — `bash scripts/db_query.sh` (SELECT·SHOW·EXPLAIN만 허용, 읽기 전용 세션). `sh`로 실행하면 문법 오류가 난다
- 지금 상태: 실행 중 쿼리, 락 대기, 상위 느린 쿼리 유형.
- 의심 쿼리가 나오면 `EXPLAIN`으로 실행 계획(인덱스 사용 여부)을 본다.
```bash
bash scripts/db_query.sh "SHOW FULL PROCESSLIST"
```
- 주의: DB 조회는 **지금 시점** 상태다. 지나간 구간은 `performance_schema`의 누적 통계와 지표로 추정한다.

**3-3. 로그**
- 로그 파일이 있으면 해당 구간의 에러, 예외, 느린 요청을 찾는다.
- 없으면 결과에 "로그 없음"이라고 명시하고 넘어간다.

**3-4. 최근 변경 (코드와 DB 둘 다)**
- 코드: 이상 시작 시각 전후의 `git log --since/--until`과 변경 파일. 대상 API와 관련된 코드(서비스, 리포지토리, 설정) 변경이 있는지 본다.
- **DB 스키마**: 인덱스·테이블 변경(DDL) 기록과 인덱스 상태(`IS_VISIBLE`)를 확인한다. 쿼리는 `references/checklist.md`의 "최근 변경"에 있다. 코드가 그대로인데 쿼리가 갑자기 인덱스를 못 탄다면 가장 먼저 의심한다.

## 결론 내리기 전 점검
- **"같은 대상이 직전에는 정상이었다"는 반대 근거가 있으면, 그사이 무엇이 바뀌었는지 찾기 전에는 결론 내리지 않는다.** 코드가 원인이라면 정상 구간에도 똑같이 느렸어야 한다.
- 개선 방안이 정상 구간과 이상 구간의 **차이**를 설명하는지 확인한다.

## 4. 결과 출력 (이 형식 그대로)

```markdown
## 요약
(한두 문장: 무엇이, 언제, 얼마나, 가장 유력한 원인)

## 원인 후보 (가능성 높은 순)
### 1. <원인> — 가능성 높음/중간/낮음
- 근거: <지표/쿼리 결과, 시각, 이상 구간 값 vs 정상 구간 값>
- 반대 근거: <있으면>

## 확인한 것 / 못 한 것
- 확인: 지표 ○, DB ○, 로그 ×(파일 없음), 최근 변경 ○
- 추가 확인 필요: <무엇을, 어떻게>

## 개선 방안
- 즉시 (사람 승인 필요): <재시작, 설정 변경 등>
- 근본 해결: <코드, 인덱스, 구조 변경>
```
