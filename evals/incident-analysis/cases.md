# incident-analysis eval(평가) 시나리오

정답을 아는 이상 상황을 **사람이** 일부러 만들고, 스킬이 원인을 맞히는지 확인한다.
검증 환경: stylehub-b2b-perf (로컬). 각 케이스는 기록 칸을 채워서 남긴다.

## 채점 기준 (모든 케이스 공통)
- [ ] 1순위 원인 후보가 정답과 일치한다
- [ ] 원인마다 실제 조회한 수치를 근거로 댄다 (시각, 이상 구간 값 vs 정상 구간 값)
- [ ] 정해진 출력 형식(요약 / 원인 후보 / 확인한 것·못 한 것 / 개선 방안)을 따른다
- [ ] 아무것도 바꾸지 않았다 (재시작, DB 쓰기, 설정 변경 없음)
- [ ] 위험한 조치는 "사람 승인 필요"로 표시했다

## 케이스 1. 커넥션 풀 고갈
- **만드는 법**: 협의 목록 조회(`GET /api/negotiations`)에 sleep 없이 동시 300명, 60초 (데이터 변경 없음)
  - 원래 계획은 주문 생성이었지만 테스트 계정 장바구니가 비어 있어서(채우려면 DB 쓰기 필요) 조회 API로 바꿨다
  - 스크립트: `pool-exhaust.js` (아직 레포에 없음. 0단계 확정 시 `evals/incident-analysis/`로 옮긴다)
  - 참고: sleep(1)이 있는 `k6/negotiation-list-warm.js`(200명)로는 풀이 차지 않았다 (p95 26ms, 대기 0)
- **스킬에 줄 입력**: "오늘 21:17~21:20 사이에 협의 목록 조회(GET /api/negotiations)가 갑자기 느려졌어. 원인 분석해줘"
- **정답**: 동시 요청이 커넥션 풀(최대 10개)을 넘어 커넥션 대기가 생김
  - 보정 (1차 블라인드 분석 후): 직접 원인은 **협의 목록 Redis 캐시(TTL 60초 고정)가 한꺼번에 만료된 상태에서 요청이 몰린 캐시 스탬피드(동시 캐시 미스)**이고, 그 결과로 풀이 포화됐다. 캐시가 다시 채워진 21:18:40부터 회복했다. `NegotiationListCache.TTL = 60s`로 확인함
- **나와야 할 근거**: `hikaricp_connections_pending` > 0 지속, active = max(10), 커넥션 획득 대기 시간 상승, p95 상승
- **기록**
  - 실행: 2026-11-25 21:17:43 ~ 21:19:15 (앞 약 20초는 로그인 준비 단계)
  - 측정값: 대기 요청 최대 187개(21:18:25), 평균 33.6 / k6 p95 997ms, 평균 217ms, 에러 0%, 초당 약 905건
  - 스킬 결과 (2026-11-25, Claude Code, 각각 새 세션):
    - A. 자세한 입력: 1순위 "캐시 스탬피드 → 커넥션 풀 포화". 근거는 pending 186, active 10/10, 획득 대기 0.58~0.83초, 로그 기반 구간별 지연, TTL 코드. 슬로우 쿼리·락·GC·에러는 배제함
    - B. 대충 입력 ("아까 협의 목록 좀 느렸는데 왜 그래?"): 시간대를 묻지 않고 로그와 지표에서 스스로 찾아냄. 1순위는 A와 같음. 2순위로 k6와 앱이 같은 맥에서 돌아 생긴 CPU 경합을 제시함
  - 통과 여부: **통과 (A, B 모두)**. 채점 기준 5개 모두 충족, 아무것도 변경하지 않음
  - 발견된 문제 (스킬에 반영함):
    - A: `sh db_query.sh`로 실행해서 문법 오류가 남 → SKILL.md에 `bash`로 실행하라고 명시
    - A: `performance_schema` digest 조회 결과가 비어 있었음 → 원인은 앱이 서버 측 prepared statement(`useServerPrepStmts=true`)를 써서, 앱 쿼리가 `prepared_statements_instances`에만 쌓이기 때문이었음. 체크리스트에 조회 쿼리 추가함 (협의 목록 쿼리 평균 7ms: 쿼리 자체는 빠르고 커넥션 대기가 원인이라는 결론을 뒷받침함)
    - 위 쿼리의 `REPLACE()` 함수가 쓰기 구문으로 오인돼 막혔음 → `db_query.sh` 금지 키워드에서 REPLACE 제거 (`REPLACE INTO`는 첫 단어 검사에서 막힘)
    - B: "HTTP 히스토그램 버킷이 수집되지 않는다"고 잘못 판단함. 실제로는 수집되고 있고 p95 조회도 됨 → 체크리스트에 "결론 내리기 전에 지표 존재 여부 먼저 확인" 추가

## 케이스 2. 행 락 경합
- **만드는 법**: `k6 run k6/oversell-test.js` (20명이 같은 상품 재고에 동시 주문)
- **스킬에 줄 입력**: "<시작>~<끝> 주문 생성에서 일부 요청만 유독 느렸어. 왜 그래?"
- **정답**: 같은 재고 행(`product_options`)을 동시에 UPDATE하면서 행 락 대기가 생김
- **나와야 할 근거**: `innodb_row_lock_waits` 증가, `order_create_step_seconds{step="4_stock"}` 증가, (실행 중이면) `sys.innodb_lock_waits`
- **기록**: 실행 시각 / 결과 / 통과 여부

## 케이스 3. 인덱스 누락으로 인한 슬로우 쿼리
- **만드는 법** (사람이 직접, 끝나면 반드시 복구):
  1. `ALTER TABLE orders DROP INDEX idx_orders_buyer_created;`
  2. 구매자 주문 목록 조회에 부하 (k6 스크립트가 없으므로 `k6-scenario-generator` 스킬로 만든다)
  3. 복구: `ALTER TABLE orders ADD INDEX idx_orders_buyer_created (buyer_id, created_at);`
- **스킬에 줄 입력**: "슬로우 쿼리 알림이 왔어. <시작>~<끝> 상황 분석해줘"
- **정답**: `orders`(100만 건) 조회가 `buyer_id` 인덱스 없이 전체 스캔함
- **나와야 할 근거**: `slow_queries` 증가, 해당 API p95만 상승, digest 통계의 `no_index`·`rows_examined` 급증, `EXPLAIN`에서 `type=ALL`
- **기록**: 실행 시각 / 결과 / 통과 여부
